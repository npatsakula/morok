# Происхождение ядер

Строка профиля «`r_128_3_32_4_2_2_2_4_4_192_2` — 100 мс» описывает форму ядра, но не
отвечает, чьё это ядро. На второй вопрос отвечает происхождение: каждое запущенное ядро
знает путь модуля, место вызова или узел ONNX, для которого его построили, а профайлер
сводит время по этому пути — по слоям, по блокам, по стадиям.

Эта страница — руководство пользователя: как включить, как разметить модель и как читать
вывод. Сам механизм (поле на каждом узле, входящее в hash-consing и снимаемое на разрезе на
ядра) кратко описан в конце, а подробно — на страницах [дизайна IR](./ir-design) и
[бестиария операций](./op-bestiary).

---

## Как включить

По умолчанию захват выключен и в выключенном состоянии не стоит ничего: узлы не несут
происхождения, а хеши байт в байт совпадают со сборкой без этой возможности. Два
переключателя:

| Переключатель | Эффект |
|--------|--------|
| `SVOD_ORIGIN=1` | захват включён для каждого потока процесса |
| `SVOD_ORIGIN_DEPTH=<n>` | сводки оставляют первые `n` сегментов пути (не задано или `0` — полный путь) |

```bash
SVOD_DEVICE=AMD:0 SVOD_ORIGIN=1 cargo run --release -p svod-model --example gigaam_infer -- \
    audio.wav --profile --origin-depth 3 --profile-json profile.json
```

В тестах переключайте захват только для текущего потока, чтобы параллельные тесты сохраняли
идентичность своих графов:

```rust
let _capture = svod_ir::origin::capture_for_thread(true); // restored on drop
```

## Откуда берётся происхождение

Происхождение — это путь из кадров, корень первым. Кадр бывает одного из четырёх видов:

| Кадр | Отображается как | Кем открывается |
|-------|-------------|-----------|
| `Module` | `encoder.layers.3.ffn1` | код модели, по одному сегменту на модуль |
| `Label` | `ctc_head`, `initializer` | стадии пайплайна, импортёр ONNX, эмбеддеры |
| `Onnx` | `/encoder/Conv` или `#12:MatMul` | импортёр ONNX, по одному на узел и на ветку подграфа |
| `Call` | `@ matmul model/src/gigaam/encoder.rs:262` | каждая публичная операция `Tensor`, автоматически |

Кадр `Call` — это плоский слой «файл:строка» под путём модуля. Публичная операция открывает
его на входе, и побеждает самый внешний: операция, собранная поверх других операций
(`linear` поверх `matmul`), запишет строку пользователя один раз и никогда — собственный
исходник svod. Слои модулей выше добавляет уже код модели.

### Разметка Rust-модели

В `forward` открывайте скоуп на каждый модуль — с тем же именем, каким записали бы его
префикс в state-dict. В крейте модели есть помощники ровно для этого:

```rust
use svod_ir::origin::OriginScope;
use crate::state::{scoped, scoped_index};

fn forward(&self, x: &Tensor) -> Result<Tensor> {
    let x = scoped("subsampling", || self.subsampling.forward(x))?;
    let mut x = x;
    for (i, layer) in self.layers.iter().enumerate() {
        x = scoped_index("layers", i, || layer.forward(&x))?;   // layers.0, layers.1, …
    }
    scoped("final_norm", || self.final_norm.forward(&x))
}
```

Каждый модуль открывает только свой сегмент; вложенность восстанавливает полный путь,
поэтому напечатанный в профиле путь совпадает с префиксом ключа state-dict у тех весов,
которых ядро коснулось. GigaAM и Whisper размечены именно так, и тест проверяет, что оба
набора путей совпадают.

Стадии пайплайна — это метки в корне:

```rust
let _stage = OriginScope::label("ctc_head");
let plan = model.prepare_with_config(&config)?;   // every kernel below is ctc_head.…
```

Всё, что построено вне скоупа, попадает в строку `<unattributed>`.

### ONNX-графы

Делать ничего не нужно. Импортёр открывает по одному кадру `Onnx` на узел (индекс, имя, тип
операции, домен, opset) и по `Label` на каждую ветку подграфа (`then_branch`, `else_branch`)
под тем узлом, которому она принадлежит, поэтому тело `If` читается как
`#7:If.then_branch.#0:Add`. Инициализаторы и входы графа лежат под `initializer` и `input`.

### Рукописные ядра

Ядро `tk` привязывается к скоупу, активному в момент его построения, — правило то же, что и
для графового ядра. Планировщик никогда не видит его тела, поэтому конструктор ядра сам
собирает и снимает происхождение; два слоя, запускающие одно и то же рукописное ядро,
по-прежнему делят одну скомпилированную программу.

## Как читать вывод

При включённом захвате `--profile` печатает обычную таблицу по ядрам, а следом — две сводки.
Пример — энкодер GigaAM v3, f16, одно 60-секундное окно на gfx1151, обрезка на глубине 3:

```
519 dispatches (519 GPU-stamped), total 444.237 ms
  total ms  count    mean µs      %  name
   103.183     16     6448.9   23.2  r_128_3_32_4_2_2_2_4_4_192_2n1
   100.305     16     6269.1   22.6  r_128_3_32_4_2_2_2_4_4_192_2
    80.530     32     2516.6   18.1  r_128_12_32_4_2_2_2_4_4_48_2
    …
origin rollup (depth 3, exclusive; rows sum to the total):
  total ms  count    mean µs      %  origin path
    27.833     32      869.8    6.3  ctc_head.GigaAmCtcJit.layers.3
    27.678     32      864.9    6.2  ctc_head.GigaAmCtcJit.layers.9
    27.620     32      863.1    6.2  ctc_head.GigaAmCtcJit.layers.0
    …
    23.334      2    11666.8    5.3  ctc_head.GigaAmCtcJit.subsampling
     0.661      4      165.2    0.1  ctc_head.GigaAmCtcJit.head
     0.131      1      131.0    0.0  ctc_head.GigaAmCtcJit
     0.007      1        6.6    0.0  <unattributed>
origin rollup (depth 3, inclusive; parents contain children, rows overlap):
  total ms  count    mean µs      %  origin path
   444.237    519      855.9  100.0  ctc_head
   444.237    519      855.9  100.0  ctc_head.GigaAmCtcJit
    27.833     32      869.8    6.3  ctc_head.GigaAmCtcJit.layers.3
    …
```

Как это читать:

- **Exclusive** относит каждый запуск ровно один раз — к его *основному* происхождению:
  скоупу, который породил сохраняемое ядром значение. Строки не пересекаются и в сумме дают
  целое, поэтому шестнадцать строк `layers.N` плюс `subsampling`, `head` и остаточная строка
  `GigaAmCtcJit` дают 444 мс. Шестнадцать слоёв по 32 запуска на каждый — это весь энкодер;
  разброс по слоям (от 25.3 до 27.8 мс) реален, и именно на него вы посмотрите первым делом.
- **Inclusive** относит запуск ко всем предкам каждого происхождения, слитого в это ядро.
  Родительская строка включает дочерние, поэтому у `ctc_head` — 100 %, а строки
  пересекаются. По ней видно, сколько времени блока прячется в ядрах, слитых через границы
  модулей.
- **Глубина** — это число оставляемых сегментов пути. Глубина 3 даёт здесь строки по слоям;
  глубина 4 разбивает слой на `ffn1`, `mhsa`, `conv`, `ffn2`, `final_norm`; лист хранит
  полный путь. Кадры `Call` никогда не образуют ключей сводки — они остаются деталью в
  строках ядер и в JSON.
- Ядро, слившее два модуля, сводка exclusive относит к тому модулю, чьё значение оно
  сохраняет (сложение остаточной связи попадает на слой, а не на `ffn2`), а inclusive — к
  обоим сразу.

`Whisper` печатает тот же раздел через `render_table()`; так же поступает любой `RunProfile`.

### JSON

`--profile-json out.json` (или `RunProfile::to_json()`) записывает по одному документу на
прогон:

```json
{
  "origin_depth": 3,
  "stages": [{
    "name": "ctc_head", "wall_ms": 463.8, "gpu_ms": 444.2, "dispatches": 519,
    "kernels": [{
      "name": "r_128_3_32_4_2_2_2_4_4_192_2", "count": 1, "total_ms": 6.3,
      "origin": "ctc_head.GigaAmCtcJit.layers.3 @ add model/src/gigaam/encoder.rs:746",
      "origin_id": 41, "origins": ["…"], "origin_ids": [41, 39]
    }],
    "origins_exclusive": [{ "path": "ctc_head.GigaAmCtcJit.layers.3", "count": 32, "total_ms": 27.8, "percent": 6.3, "kernels": [] }],
    "origins_inclusive": []
  }],
  "origins": [{ "id": 41, "parent": 40, "frame": { "Module": { "name": "layers.3" } } }]
}
```

Ключ строки ядра — это точка входа *и* основное происхождение, поэтому одна и та же
программа появляется по разу на каждый скоуп, который её запускал. В `origins` попадают
только те кадры, на которые сослался прогон, замкнутые по `parent`, поэтому идентификаторы
разрешаются и без процесса, записавшего файл.

## Потоки

Состояние захвата — потоколокальное: переключатель, текущий скоуп и признак того, что этот
скоуп — кадр вызова. Скоупы не уходят вслед за работой на другие потоки; guard скоупа —
`!Send` и восстанавливает тот поток, в котором был открыт. Отсюда вытекают правила:

- Стройте граф в том потоке, который открыл скоупы. GigaAM и Whisper так и делают; метка
  стадии, открытая вокруг `prepare_with_config`, покрывает всё, что построено внутри неё.
- Планирование и компиляция идут вне скоупов (`OriginScope::suspend`) — и на вызывающем
  потоке, и на воркерах rayon одинаково, — поэтому окружающий скоуп никогда не протекает в
  тело ядра: привязка к этому моменту уже собрана на CALL.
- Чтобы перенести скоуп на воркер, который вы порождаете сами, захватите `origin::current()`
  и переустановите его там через `origin::install(id)`. Свой переключатель воркеры
  инициализируют из `SVOD_ORIGIN`, как и любой другой поток.
- BEAM-поиск идёт в дочернем процессе на телах ядер без происхождения и скоупов не видит
  вовсе.
- **Асинхронный код:** скоупы обязаны вкладываться друг в друга, поэтому не удерживайте
  скоуп через `.await`. Откройте скоуп, синхронно постройте граф, отпустите его — и только
  потом ждите. Guard — `!Send`, поэтому future, который держит его живым через await, не
  запустить на многопоточном исполнителе, а отладочная сборка паникует, когда две задачи
  чередуют скоупы в одном потоке (guard отпущен, пока более поздний ещё активен). Построение
  графа в svod синхронно, так что естественно написанный код это правило уже соблюдает.

## Стоимость и компромиссы

- **Выключено:** ничего. Одно потоколокальное чтение на узел, никаких аллокаций, хеши без
  изменений.
- **Включено:** одно интернирование на вход в скоуп (мьютекс над ареной, сотни раз за прямой
  проход), одна потоколокальная запись на каждую публичную операцию ради кадра вызова и одна
  топосортировка на ядро на разрезе, чтобы собрать объединение. Счётчики запусков и время GPU
  у GigaAM одинаковы при включённом и выключенном захвате.
- **Идентичность меняется.** Происхождение — часть идентичности узла, поэтому два одинаковых
  выражения, построенные в разных скоупах, остаются двумя узлами, пока разрез их не снимет.
  Программ ядер это не касается — снятие возвращает дедупликацию, — но вспомогательная
  функция, которая заново строит одно и то же выражение на каждом месте вызова (ограничение
  маски, приведение таблицы, копия входа), материализует его по разу на скоуп. Вызывайте
  такие функции под `OriginScope::suspend()` либо разрешите копии унаследовать происхождение
  своего производителя; `custom_kernel` уже делает второе для своих входов. Константы,
  буферы и параметры по той же причине никогда не несут происхождения.
- **Тесты, опирающиеся на структурную идентичность** (два собранных вручную графа, от которых
  ждут hash-consing в один узел), должны запускаться с `capture_for_thread(false)`.

## Как это работает, в одном абзаце

Каждый `UOp`, построенный при активном скоупе, хранит его 4-байтный `OriginId` и подмешивает
его в свой content-хеш, поэтому одинаковые подграфы из разных скоупов остаются различимы
вплоть до rangeify. На разрезе на ядра `split_store` один раз обходит тело, берёт
происхождение сохраняемого значения как основное, а объединение — как множество, проставляет
оба на `CallInfo` у `CALL` ядра и пересобирает тело со снятыми происхождениями. Всё, что идёт
после разреза — оптимизатор, BEAM, кодогенерация, любой кэш ядер, — видит AST без
происхождения.
План копирует привязку с CALL на каждую подготовленную операцию, профайлер — на каждый
`KernelProfile`, а сводки обрезают цепочку родителей до запрошенной глубины.
